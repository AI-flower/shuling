## 2. Hacker News — Show HN alternative (upgrade-infra angle)

**Title** (78 chars):

```
Show HN: install.sh upgrade-all – an agent-native upgrade script for AI skills
```

**Body** (target 200–300 words, HN tone: skeptical, specific, honest tradeoffs):

```
Each time I shipped a new version of my Claude skill, my agent had to push the user through 9 manual upgrade steps: backup, rsync the new files, run SQLite migrations, patch runtime.env for new keys, port preferences into the new schema, update the scheduler prompts, pip install new deps, run preflight, run schema validation. Across 3 install targets (Claude Code, Codex, Hermes — users often have all three side-by-side), that's 27 steps, and any one of them failing left the user in a half-upgraded state. So I wrote install.sh upgrade-all.

The contract is boring on purpose:

  $ ./install.sh upgrade-all --json
  { "targets": [
      {"name": "claude-code", "status": "ok", "from": "2.3.0", "to": "2.4.0", "steps": [...]},
      {"name": "codex", "status": "failed", "failed_step": "migrate", "error": "..."},
      {"name": "hermes", "status": "ok", ...}
  ]}

Six steps per target, same order every time: backup → rsync → migrate → upgrade_hook → pip → preflight. A __migrations table tracks which schema versions have been applied, so migrate is idempotent — re-running upgrade-all is safe. An upgrade-hooks/v2.4.0.sh file captures non-DB side effects (prompt rewrites, pref-file shape changes) as code instead of as instructions the agent has to remember. requirements.txt locks deps. Failure in one target doesn't block the others; the JSON tells you which ones to re-run with --target.

Tradeoffs I won't hide: the rsync model assumes the skill's install dir is yours to overwrite — fine for personal installs, would need a merge strategy for shared team installs. The JSON schema is still v0, and I haven't version-pinned it yet. upgrade-hooks are bash, which is a choice I might regret once hook #4 ships. Six steps is the most I'd want; past that this starts wanting to be a real package manager.

Code and design notes: https://github.com/AI-flower/shuling

What I'd most like feedback on: the JSON contract. If you were an agent consuming the output of upgrade-all to report to your user, what fields would you need that I'm missing? And is "one __migrations table per target" the right unit, or should it be one table per skill across all targets?
```

## 4. Medium / Dev.to 长文大纲

**Title**: How to design upgrade infrastructure for AI skills

**Audience**: AI agent engineers; skill / tool-chain builders shipping v2+ of anything an agent executes.

**Full length**: 2000–2500 words (outline only below — user can commission full draft later).

---

### §1. The moment you realize a skill is software (≈250 words)

- The v1 "upgrade story": `git pull`. Works until it doesn't.
- The v8 reality on ShuLing: 9 manual steps the *user's agent* has to run, in order, on each of 3 install targets. 27 steps total.
- What breaks: users end up in partially-upgraded state. Different preferences shape on each target. Missing deps. Schema drift. The agent can't tell the user *what* is broken because no step is observable.
- The thesis: if a skill evolves, you eventually need the same boring release plumbing real software has — you just have to design it for an agent to execute, not a human.

### §2. Mapping the 9-step pain to 6 composable primitives (≈350 words)

- Walk through the actual v2.3.0 → v2.4.0 manual procedure, step by step.
- Group each step into one of 6 repeatable primitives:
  1. **backup** — snapshot current install dir + DB
  2. **rsync** — copy new skill files in place
  3. **migrate** — apply SQLite schema migrations idempotently
  4. **upgrade_hook** — run version-specific side effects
  5. **pip** — install Python deps from requirements.txt
  6. **preflight** — verify the target is healthy post-upgrade
- Show which manual step collapsed into which primitive.
- Explain why 6 is the ceiling: beyond that, you're building a package manager — at that point, use one.

### §3. `__migrations` — idempotent DB is non-negotiable (≈350 words)

- Schema of the `__migrations` table (version, applied_at, checksum).
- Why idempotence matters more for agent-driven upgrades than for human ones: retry is cheap and frequent, so re-running must be a no-op.
- 10 → 11 tables in v2.4.0: walk through the migration file for the new table.
- Anti-pattern we rejected: storing "last upgraded to" in `runtime.env`. A file-level flag breaks under concurrent invocations; a table with row-per-version doesn't.
- Drift detection via `scripts/validate.py`: compares live schema to `schema.sql`, exits nonzero on mismatch.

### §4. `upgrade-hooks/` — side effects as code, not as agent memory (≈350 words)

- The problem: prompt rewrites, preference-file reshaping, scheduler copy updates — none of these are DB migrations, but they're still version-specific side effects.
- Old approach: write the steps into release notes and hope the agent executes them right. Fails under drift.
- New approach: `upgrade-hooks/v2.4.0.sh` is executable code, committed alongside the release. The upgrade runner executes hooks in version order and records completion.
- Why bash and not Python: the hook needs to survive a broken `requirements.txt`; bash is the floor.
- Why this is specifically *agent*-friendly: an agent doesn't need to interpret a changelog paragraph, it just reads a filename.

### §5. JSON observability — the upgrade log is the contract (≈350 words)

- Show the full `--json` output shape for a 3-target run, including one failure.
- Rule: every line a human sees in `--dry-run` has a corresponding JSON event. No hidden state.
- Why this matters when the *caller* is an agent: the agent needs to report success/failure to the user with specifics. "It failed" is not a useful sentence. "Codex's migrate step failed with `table X already exists`" is.
- Independent target failure: design choice to continue past a failed target rather than abort. Rationale: in a 3-target install, blocking Claude Code's upgrade because Hermes is missing a Python package is worse than shipping 2/3 upgraded + one clear error.
- Open question: should the JSON schema itself be versioned? (Currently v0, unversioned. Leaning toward adding `"schema": "upgrade-all/v1"` before the next breaking change.)

### §6. What this generalizes to (≈250 words)

- Every skill that evolves past v3 hits some version of this wall.
- The reusable bits:
  - 6-primitive structure (you will use exactly these, or a subset).
  - `__migrations` pattern (nothing novel, just apply it to skills).
  - hooks directory (once you have 2 version-specific side effects, start one).
  - machine-readable upgrade log (the day you debug a failed upgrade over a screenshot, you'll wish you had one).
- What doesn't generalize:
  - The specific bash/Python mix — your skill's stack decides this.
  - The target-name list — your multi-host story is yours.
- Closing line: _"Skills are software. The boring release plumbing is not the unsexy part — it's the part that decides whether v8 is usable at all."_

## Appendix — tone / duplication guardrails vs. v2.3.0 posts

- v2.3.0's story was **Skill-as-Brain** (Markdown is the program). Do not re-pitch that here.
- v2.3.0's metrics to stop reusing: "1208 lines of Markdown", "Bayesian preference learning", "BRAIN.HANDS.CALIB semver". They belong to the previous release.
- v2.4.0's metrics to use: **9 → 1 steps**, **6 primitives**, **10 → 11 tables**, **487 → 979 LOC of install.sh**, **3 targets side-by-side**.
- Language to avoid (carried from HN playbook): "production-grade", "enterprise-ready", "game-changer", "paradigm shift", "I built X so you don't have to", "MIT open source!" as an opener, emoji in HN title/body.
- Language to favor: specific numbers, named primitives (backup/rsync/migrate/upgrade_hook/pip/preflight), honest tradeoffs, concrete failure modes.
- The star of this release is the **method**, not the numbers. Lead with the procedure you replaced, not with a feature list.
